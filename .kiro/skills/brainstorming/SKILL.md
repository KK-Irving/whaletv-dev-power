# Skill: 先设计再编码（Brainstorming）

## 目的

在动手修改代码之前，先进行方案探讨和设计验证，减少返工，确保修改方向正确。

## 核心原则

**不要直接跳入代码修改。** 先理解问题 → 探索方案 → 确认方向 → 再动手。

## 触发时机

以下场景必须先进行 brainstorming：

| 场景 | 触发条件 |
|------|---------|
| Bug 修复 | Issue 描述复杂，涉及多个模块 |
| 新功能开发 | 需要修改 3 个以上文件 |
| 重构 | 涉及接口变更或架构调整 |
| 不确定方案 | 存在多种可行方案时 |

以下场景可以跳过 brainstorming：

| 场景 | 条件 |
|------|------|
| 简单修复 | 明确知道改哪一行（如拼写错误、配置值修改） |
| 翻译更新 | 纯文本替换 |
| 版本号更新 | 机械性操作 |

## Brainstorming 流程

### ① 问题理解

向用户确认：
```
我理解的问题是：[一句话总结]
涉及的模块：[模块列表]
预期的修改范围：[文件/目录]

这个理解正确吗？
```

### ② 方案探索

列出可能的方案（至少 2 个，除非只有一种合理做法）：
```
方案 A：[描述]
- 优点：...
- 缺点：...
- 影响范围：...

方案 B：[描述]
- 优点：...
- 缺点：...
- 影响范围：...

我推荐方案 [X]，因为 [理由]。
```

### ③ 方向确认

等待用户选择或确认方案后再动手。

### ④ 实施计划

确认方案后，列出具体的修改步骤：
```
实施计划：
1. 修改 [文件A] — [做什么]
2. 修改 [文件B] — [做什么]
3. 验证 — [如何验证]
```

## 与现有工作流的融合

### PR/CR 工作流中的应用

在步骤 ② "分析问题" 和步骤 ③ "定位代码" 之间，如果问题复杂，插入 brainstorming：

```
① 获取 Issue
② 分析问题
   ↓ [如果问题复杂]
   ② .5 Brainstorming（方案探索 + 用户确认）
   ↓
③ 定位代码
④ 修改代码
```

### Bug 分析工作流中的应用

在输出分析报告的"修复建议"部分，如果有多种修复方向，使用 brainstorming 格式展示：

```
### 修复建议

方案 A：在 XXX 处添加空值检查
- 影响范围：仅 1 个文件
- 风险：低

方案 B：重构 YYY 的调用链
- 影响范围：3 个文件
- 风险：中等，但更彻底

推荐方案 A（快速修复），如果时间允许建议方案 B。
```

## 关键约束

- Brainstorming 不是必须的——简单明确的修改直接执行
- 方案探索不超过 3 个选项（避免决策疲劳）
- 如果用户说"直接改"或"不用讨论"，跳过 brainstorming
- 方案描述要简洁，每个方案不超过 3 行
- 记住用户的选择偏好（如果用户总是选择快速方案，后续默认推荐快速方案）
